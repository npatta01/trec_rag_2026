Orientation

What Is This Competition About?

TREC RAG asks for evidence retrieval plus cited answer generation: find useful documents for a complex information need, then write an answer whose claims are visibly grounded in those documents.

2026 tasks

The 2026 track has Retrieval and RAG tasks. Retrieval measures the evidence list; RAG measures the end-to-end answer with citations.

Retrieval output

Retrieval output is a ranked list of document IDs in the six-column TREC format:

topic_id Q0 docid rank score run_id

RAG output

RAG output is human-readable prose with sentence-level citations, not raw chunks. Every substantive generated answer sentence should be supported by citations.

ClimbMix

What Is ClimbMix?

ClimbMix is the 2026 evidence collection: a broad curated web/pretraining-style collection rather than a single-domain corpus. The official unit is a ClimbMix row/document with a ClimbMix docid.

Document anchor

Systems can chunk locally for indexing, reranking, or generation, but final retrieval rows and RAG references should map back to official ClimbMix document IDs.

Baseline path

Pyserini/BM25 baseline infrastructure gives teams a plain starting point: build a lexical index, run a standard ranked search, then inspect where stronger methods help.

System impact

The practical discipline is traceability. Internal chunks may help the model read evidence, but submitted IDs and citations need to resolve to the official ClimbMix documents.

2025 Context

What Happened In 2025?

TREC RAG 2025 used MS MARCO V2.1 segmented documents and long narrative information needs, not only short keyword queries. The overview paper reports 105 narratives, with official assessed analysis centered on 22 selected narratives.

  • Task framing The 2025 overview describes four tasks: Retrieval, Augmented Generation, Retrieval-Augmented Generation, and Relevance Judgment.
  • System behavior Strong approaches treated each narrative as a multi-facet request, so answer quality depended on broad evidence coverage as well as careful citation and synthesis.
  • Technique example UTokyo 4method_merge is useful as a 2025 Retrieval task example of combining hybrid retrieval, HyDE-style querying, Reciprocal Rank Fusion (RRF), and reranking before final ranking.
Technique Gallery

Approaches People Used In 2025

Read the 2025 systems as a menu of useful techniques, not only as a leaderboard. Most strong RAG pipelines are built from small, understandable moves: find candidate evidence, merge and reorder it, choose what matters, write with citations, then check the answer.

Retrieval

BM25 / lexical retrieval

Search by keyword overlap. Documents that share rare or distinctive words with the query rise toward the top.

When to use it

Use it as the first baseline, especially when the question includes names, IDs, product terms, legal phrases, or other wording that must match exactly.

Watch out for

It can miss useful evidence when the document says the same idea with different words.

query: "climbmix document ids citation format"
BM25 favors pages with those exact terms.
Retrieval

Query expansion

Add related phrases to the original query so search has more ways to find the same idea.

When to use it

Use it when users use one term but the collection may use another, such as "cost" versus "price" or "doctor" versus "clinician".

Watch out for

Extra words can drift away from the intent and pull in documents that sound related but answer the wrong question.

original: "solar rebate rules"
expanded: "solar rebate rules tax credit incentive eligibility"
Retrieval

Query decomposition

Split a long narrative need into smaller searches, each aimed at one part of the answer.

When to use it

Use it for questions with multiple facets, time periods, entities, or comparison points that one search might not cover.

Watch out for

Vague subqueries can make the system look busy while still missing the facts the final answer needs.

need: "Compare benefits and risks"
search 1: "main benefits"
search 2: "reported risks"
Retrieval

Dense retrieval

Turn queries and documents into embeddings, then retrieve text that is close in meaning even when the words differ.

When to use it

Use it when paraphrases matter, when users ask in everyday language, or when the collection uses varied wording.

Watch out for

It may retrieve passages that are topically similar but do not actually answer the question.

"How do I appeal?" can find
"request a review of the decision"
Retrieval

Hybrid sparse plus dense retrieval

Run keyword search and embedding search together, then combine their strengths so exact terms and paraphrases both get a chance.

When to use it

Use it when exact wording matters but you still need semantic coverage. UTokyo's documented 2025 Retrieval run is a useful example of this family with hybrid retrieval, HyDE-style querying, Reciprocal Rank Fusion (RRF), and reranking.

Watch out for

Two retrievers mean more settings to tune, and bad merging can bury the best evidence instead of promoting it.

candidates = bm25(query) + dense(query)
next: fuse, rerank, then select evidence
Retrieval

SPLADE-style learned sparse retrieval

Use a model to predict useful weighted keywords, keeping the speed and transparency of sparse search while adding learned expansion.

When to use it

Use it when you want inverted-index behavior but need help matching related terms that plain keyword search would miss.

Watch out for

It adds model complexity, indexing cost, and another source of retrieval behavior to debug.

Fusion

Reciprocal Rank Fusion

Merge several ranked lists by rewarding documents that appear near the top of one or more lists.

When to use it

Use it when you have BM25, dense, expanded-query, or decomposed-query results and want a simple, robust way to combine them.

Watch out for

It cannot rescue evidence that no retriever found in the first place.

score(doc) = sum(1 / (k + rank_in_each_list))
Retrieval

HyDE

Ask a model to draft a hypothetical answer, then search with that draft so retrieval has richer language to match against.

When to use it

Use it for abstract or underspecified questions where the original query is too thin to retrieve good evidence.

Watch out for

If the hypothetical answer invents the wrong framing, retrieval can drift toward convincing but irrelevant material.

user query -> hypothetical answer
hypothetical answer -> retrieval query
Reranking

LLM reranking

Use a stronger model to read candidate passages and reorder them by how useful they are for the user's actual need.

When to use it

Use it after broad retrieval when you can afford extra latency or cost to improve the top evidence shown to the generator.

Watch out for

It is slower and costlier than first-stage retrieval, and a vague prompt can reward fluent but weak evidence.

Prompt: "Rank these passages by direct support
for answering the narrative."
Reranking

Evidence selection

Choose the small set of chunks the answer writer will actually use, rather than sending every retrieved passage forward.

When to use it

Use it before generation when the candidate pool is large, repetitive, or mixed with distracting background material.

Watch out for

Missing one important facet can produce a polished answer that is still incomplete.

Generation

Citation-first generation

Plan the answer around cited evidence before writing the final prose, so each important claim has a source.

When to use it

Use it when the evaluation rewards traceable claims and when readers need to inspect where each part of the answer came from.

Watch out for

The answer can become stiff if it lists citations without synthesizing what the evidence means.

claim -> supporting doc id -> sentence
repeat before drafting the final response
Quality

Post-generation checks

Review the drafted answer for uncited claims, missing facets, wrong citations, and statements the evidence does not support.

When to use it

Use it as the final gate before submission, especially for long answers with many claims and citations.

Watch out for

A weak checker may rubber-stamp errors, so it needs clear rules and should inspect both the answer and the cited evidence.

checklist: cited? supported? complete?
flag anything that fails before submission
Transition

What Changed From 2025 To 2026?

The 2026 track keeps the core retrieval-plus-synthesis challenge but changes the evidence collection, task structure, and citation target through ClimbMix.

Dimension 2025 2026
Corpus MS MARCO V2.1 segmented documents. ClimbMix document rows.
Tasks Retrieval, AG, RAG, and RJ. Retrieval and RAG.
Generation setup Fixed-evidence AG plus end-to-end RAG. Participant-owned retrieval and generation for RAG.
Evidence IDs MS MARCO segment IDs. ClimbMix document IDs.
Main lesson Long narratives reward coverage across facets. The same lesson applies over a broader web-style corpus.
Strategy

How I Would Approach 2026

The official-style simple BM25 baseline should be title-first: use the topic title as the default query because it is fast, debuggable, and hard to fool yourself with. Use the narrative to understand the need, decompose facets, fuse candidate lists, rerank candidates, select evidence, guide generation, and run citation checks; treating title plus narrative as the raw query is an experiment to label separately, not the default baseline.

Search broadly

Start with the title query, then use the narrative to split the need into concrete facets when it clearly asks for causes, impacts, responses, timelines, or affected groups.

Fuse and rerank

Combine the candidate lists so useful documents from weaker facet searches survive, then rerank for direct support rather than surface keyword overlap alone.

Write from evidence

Select the smallest set of passages that covers the answer, draft only supported claims, and check that every citation points to evidence that really says the thing.

Direct title BM25 is the control run

This asks BM25 to match the topic title as the default query. It is useful because every later experiment should beat this run on recall or evidence quality, not just look more sophisticated. A title-plus-narrative query can be tried as a separate experiment, while the narrative remains essential for understanding facets, reranking, evidence selection, and generation.

query = title
# Use narrative for facets, reranking, evidence selection, and generation.
search(climbmix_bm25, query, top_k=100)

Facet decomposition improves recall for broad narratives

Many TREC RAG topics are not single-fact questions. A narrative might ask what caused an issue, who was affected, and what responses followed. Searching those facets separately gives each angle a chance to retrieve documents, then fusion keeps documents that are consistently useful across lists.

facet_queries = ["wildfire smoke respiratory health impacts", "wildfire smoke affected groups children older adults", "wildfire smoke public health responses"]
candidates = rrf(search_each(facet_queries))

Decomposition can add noise when facets are vague

The danger is turning a specific narrative into generic search strings. A query like "public health responses" may retrieve pages about any issue in ClimbMix. Keep the facet label, but anchor it with topic terms copied from the narrative so the search expands coverage without drifting away.

bad = "public health responses"
better = "public health responses to wildfire smoke exposure"

Retrieved documents become a cited answer

After reranking, choose passages that support distinct pieces of the answer. The generator should write sentence by sentence from those passages, attach zero-indexed citation indices into the ordered reference list, and preserve the official-style top-level JSONL object shape.

{
  "metadata": {
    "team_id": "example-team",
    "run_id": "title-bm25-rag-v1",
    "type": "automatic",
    "narrative_id": "2026-001",
    "title": "Health impacts of wildfire smoke exposure",
    "narrative": "Summarize the reported health impacts of wildfire smoke exposure and identify which groups were most affected.",
    "prompt": "Answer using only the provided ClimbMix evidence."
  },
  "references": [
    "shard_01789_3390",
    "shard_02144_1022",
    "shard_04418_2207"
  ],
  "answer": [
    {
      "text": "The selected evidence links wildfire smoke exposure to respiratory health impacts, with children, older adults, and people with pre-existing conditions described as higher-risk groups.",
      "citations": [0, 1]
    },
    {
      "text": "The response evidence describes public-health guidance and temporary protective measures rather than a single permanent policy fix.",
      "citations": [2]
    }
  ]
}
Evaluation

How To Think About Grading

Think of grading as two linked questions: did the system find evidence that covers the need, and did the final answer make only claims that the evidence can support?

Retrieval relevance is facet-aware

A document can be more valuable if it helps answer multiple parts of a long narrative, such as causes, impacts, timelines, and affected groups. A narrower document can still be useful, but broad facet coverage often matters more than matching one phrase exactly.

RAG quality is coverage plus support

A strong answer covers the important pieces of the information need and cites evidence that actually supports each factual claim. Fluency helps readers, but it does not compensate for missing facets or weak citations.

Uncited claims create risk

Uncited factual claims are liabilities. Connective prose may not always need citations, but factual answer claims should be cited or removed before submission.

Check the chain

For each sentence, ask: is this part of the topic important, is the statement factual, and do the cited references say the same thing? If any answer is no, revise the answer or replace the evidence.

2026 submission formats

Retrieval submissions use the standard six-column TREC row, one ranked document per line:

topic_id Q0 docid rank score run_id

RAG submissions use JSONL. Each line should keep the top-level shape of metadata, references, and answer. Citation indices in answer objects point into the zero-indexed references array.

{
  "metadata": {
    "team_id": "example-team",
    "run_id": "rag-run-01",
    "type": "automatic",
    "narrative_id": "2026-001",
    "title": "Example topic",
    "narrative": "Example narrative need",
    "prompt": "Answer using only the supplied evidence."
  },
  "references": ["climbmix-doc-1", "climbmix-doc-2"],
  "answer": [
    {
      "text": "A supported factual answer sentence.",
      "citations": [0]
    },
    {
      "text": "Another supported factual sentence.",
      "citations": [0, 1]
    }
  ]
}
Development data mental model

Local development data includes 22 RAG25 topics and 30 ResearchRubrics prompts. Treat them as practice material for understanding topic shape, citation behavior, and evaluator expectations.

Development qrels, short for query relevance judgments, are judged or model-generated pools for development, not exhaustive truth over all ClimbMix. They can guide experiments and error analysis, but a missing judgment does not prove that every unjudged ClimbMix document is irrelevant.

Source caveats
  • Rankings are tied to a particular task, metric, and pool. Do not transfer a rank from Retrieval to full RAG unless the source explicitly supports that comparison.
  • A top Retrieval run is not automatically the top full RAG system. The answer-writing, citation, and support checks can change the end-to-end result.
  • Top RAG answer runs without a method writeup should be described carefully: name what the official run browser shows, but avoid inferring private pipeline details.
  • UTokyo 4method_merge remains a Retrieval-task example only: useful for learning about hybrid retrieval, HyDE-style querying, fusion, and reranking, not evidence that the same run led full RAG answer quality.
