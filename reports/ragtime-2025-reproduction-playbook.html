Executive Summary

  • RAGTIME tested time-sensitive report writing. Systems had to retrieve evidence from a multilingual news-style corpus and produce cited reports under strict length limits.
  • The main trade-off is coverage versus support. Good systems need to cover enough facts, but every factual sentence also needs evidence. Methods differ mostly in how they plan retrieval and police citations.
  • Start simple, then add planning. AMU is the clean starter baseline; GenAIus is the best next step for question-driven coverage; WueRAG teaches citation discipline; HLTCOE and IDACCS are advanced targets once the basics work.
  • The details are still here, just collapsed. Each method card gives a plain-English explanation first, then expandable implementation details and official evidence.

Start With A Ladder, Not The Whole Leaderboard

Do not try to reproduce every run. RAGTIME had many submissions, but most of the learning comes from a small set of patterns: simple dense retrieval, question planning, strict citation filtering, rerank fusion, nugget-first planning, extractive compression, lightweight retrieval, and agent workflows.

Recommended first three builds: AMU baseline for plumbing, GenAIus question-driven retrieval for multilingual coverage, and WueRAG for citation discipline. Those three expose most of the core RAGTIME trade-off before you spend weeks on multi-model rerank fusion or agentic workflows.

How to read a method card: read the plain-English box first, then the build recipe. Open the implementation drawer only when you are ready to reproduce that method. Open the evidence drawer when you want official scores, run IDs, and paper links.

Plain-Language Glossary

These terms show up throughout the report. The short definitions below are enough to understand the method cards.

RAG
Retrieval-augmented generation: search for source material first, then ask a model to write using that material.
Retrieval
The search step that decides which documents or passages the model gets to see.
Reranking
A second pass that takes search results and reorders them with a stronger, usually slower model.
Fusion
Combining several ranked lists so documents favored by multiple methods rise higher.
Nugget
A small fact or answer unit that a good report should cover.
Support
Whether a sentence is actually backed by its cited source.
Coverage
How many important facts the report includes.
MLIR
Multilingual information retrieval: retrieving useful documents across languages.
Citation Filter
A postprocessing step that removes claims whose citations are missing or invalid.

Foundation reproduction target

AMU Minimal Baseline

Why this matters: Best first reproduction target: the method is simple, well described, and gives a sanity-check baseline for schema, citations, and multilingual retrieval.

Low difficultyMedium payoff1-2 days timebox

In Plain English

This is the clean starter system. It cuts the document collection into chunks, turns each chunk into a searchable vector, pulls back the closest matches, rebuilds a few source documents, and asks the model to write a cited report.

Mental model: A simple library search: split books into pages, search for the most similar pages, then hand a few books to the writer.

How To Start

  1. 1Build only the retrieval and citation plumbing first.
  2. 2Use it as your control system before adding rerankers, question planning, or agents.
  3. 3Check that every final citation points to a real source document.

Watch out: It is easy to build and easy to debug, but it will miss facts when one query does not cover all parts of a broad topic.

Build Recipe

  • Chunk every document into roughly 5-10 sentence windows, with an 8k-character hard cap for edge cases.
  • Embed chunks with BAAI/bge-m3 and store them in Qdrant.
  • Build the query from title, background, and problem statement.
  • Retrieve top chunks by cosine similarity and reconstruct source documents from their chunks.
  • Generate JSON with GPT-5-family schema enforcement and citation dictionaries.
  • Validate character budget, JSON schema, and citation ids before scoring.

Tools And Terms You Will See

QdrantBAAI/bge-m3GPT-5 familyJSON schema

Main Pitfalls

  • Dense-only retrieval undercovers facets, so nugget coverage is the expected weakness.
  • Citations must map back to document ids, not chunk ids.
  • Do not tune against this system; keep it as the baseline control.

Implementation Details That Matter

  • Aggregate retrieved chunk scores by original document before deciding which documents enter the LLM context.
  • Pass each reconstructed source as Document ID, merged content, and relevance score; do not expose chunk ids as citation ids.
  • Set temperature to 0 and cap max tokens to about 75 percent of the requested character budget so the model has room but still respects the limit.
  • After decoding, normalize any list-style citations into dictionary form to match the RAGTIME submission schema.
  • Keep this implementation intentionally dense-only and no-rerank; its value is as a control system for ingestion, citation plumbing, and scoring.

Prompt / API Contracts

  • System prompt: output strictly valid JSON conforming to the report schema; every factual statement must be supported by provided context.
  • User prompt payload: title, background, problem statement, character limit, and reconstructed documents formatted with document id, content, and relevance score.
  • Citation rule: citations are dictionaries of document ids to confidence or score; never cite chunk identifiers.
  • Conclusion rule: include a standalone conclusion only if it is grounded in cited context.

Acceptance Checks

  • For a sample topic, confirm every cited id exists in the reconstructed document set.
  • Confirm top-15 chunk retrieval reconstructs no more than 7 documents unless you intentionally change the context budget.
  • Run the official JSON validator or an equivalent schema check before any scoring run.
  • Compare AMU-style dense retrieval against a simple BM25 baseline to quantify how much recall you lose before adding advanced methods.

Implementation Skeleton

chunks = chunk_documents(corpus, by='5-10 sentences', max_chars=8000)
qdrant.upsert(embed_bge_m3(chunks))
query = title + background + problem_statement
docs = reconstruct_documents(qdrant.search(embed(query), top_k=15))
report = llm.generate_json(request, docs, schema=cited_report_schema)

Open Reproduction Unknowns

  • The exact full system and user prompts are shown in the AMU paper, but any unavailable private prompt wording should be treated as non-essential if the schema, citation, and length constraints are preserved.
  • The paper does not make the exact Qdrant collection schema mandatory; document id, chunk id, language, text, and score metadata are the minimum needed for faithful behavior.

Primary reproduction target

GenAIus Question-Driven RAG

Why this matters: Most useful high-performing reproduction target: it turns report generation into explicit question planning, which is easy to inspect and adapt.

Medium difficultyHigh payoff3-5 days timebox

In Plain English

This system makes the model ask many focused research questions before it searches. Each question retrieves evidence for one part of the report, then the system merges repeated documents and writes from the collected answers or nuggets.

Mental model: A research assistant who writes a checklist of questions before going to the library.

How To Start

  1. 1First reproduce question generation plus per-question retrieval.
  2. 2Log the generated questions because they explain why the system found or missed evidence.
  3. 3Start with question mode before cluster mode because the intermediate answers are easier to inspect.

Watch out: Bad questions waste the retrieval budget. This method works when the questions are specific enough to cover different facets of the request.

Build Recipe

  • Use GPT-4o or a strong open model to generate targeted questions from title, background, and problem statement.
  • Retrieve a fixed budget of documents per generated question through the search API or your own retriever.
  • Merge duplicate documents and boost documents retrieved by multiple questions.
  • For question mode, answer each question from retrieved evidence, then synthesize the final report.
  • For cluster mode, extract nuggets from top documents, cluster semantically similar nuggets, then write from clusters.
  • Compare question mode for coverage against cluster mode for citation support.

Tools And Terms You Will See

Question generatorRAGTIME search API or local retrieverGPT-4oNugget clustering

Main Pitfalls

  • Question quality is the control surface; broad or generic questions waste retrieval budget.
  • Per-question retrieval quotas need a cap so long question lists do not explode cost.
  • Cluster mode may ground better but lose breadth if only one document per question is used.

Implementation Details That Matter

  • Treat question generation as the main control surface: log every generated question and attach downstream retrieved documents to it.
  • The score-summing merge is not just deduplication; it intentionally boosts documents retrieved by multiple question formulations.
  • For report generation, keep the intermediate answers or nuggets as auditable artifacts so you can diagnose whether failures came from planning, retrieval, or synthesis.
  • Question mode is likely the first reproduction because the intermediate Q/A table is easy to inspect; cluster mode is better for testing organization and citation support.
  • Keep MLIR and report-generation reproductions separate: MLIR uses the question-driven retrieval pipeline alone; report generation adds answer/nugget synthesis.

Prompt / API Contracts

  • Question prompt: generate a diverse set of targeted search questions from title, background, and description; reflect the requester's role and audience; avoid generic or overly broad questions.
  • Question output format: one plain-text question per line, prefixed as Question <number>: <question text>.
  • Answer prompt: answer a generated question using only its retrieved evidence and the original request; keep each answer to at most three sentences and cite the best supporting document.
  • Cluster prompt: group nuggets by semantic similarity into distinct aspects or dimensions, discard irrelevant nuggets, and produce an interpretable label for each cluster.
  • Final prompt: write the report from original request plus Q/A answers or clustered nuggets; every sentence should carry an appropriate citation and respect the character limit.

Acceptance Checks

  • For each topic, verify total requested retrieval depth does not exceed 1,000 before deduplication.
  • Inspect whether repeated-document score summing changes the top 20 compared with simple max-score merging.
  • Measure coverage loss when using one document per question in cluster mode versus top 10 per question in question mode.
  • Store question, retrieved ids, intermediate answers/nuggets, and final report so failures are reproducible topic-by-topic.

Implementation Skeleton

questions = llm.generate_questions(title, background, problem)
for q in questions: results += search(q, k=budget_per_question)
docs = merge_by_docid(results, score=sum_repeated_scores)
answers = [answer_question(q, top_docs(q)) for q in questions]
report = synthesize_cited_report(answers, docs)

Open Reproduction Unknowns

  • The organizer search API internals were not publicly documented by GenAIus; a faithful reproduction should either use the same API if available or report the replacement retriever clearly.
  • The paper gives prompt figures, but exact deployed system messages and retry logic may not be fully recoverable.
  • The exact number of generated questions is model-dependent; reproduce by pinning model, temperature, and prompt, then logging generated question counts.

Primary reproduction target

WueRAG Citation-Strict English Pipeline

Why this matters: Best target if you want a clean citation-grounding system: it separates recall from local precision and aggressively removes unsupported sentences.

Medium difficultyHigh payoff2-4 days timebox

In Plain English

This system is strict about citations. It searches for English evidence, builds a small local index, asks the model to cite every factual sentence, then deletes sentences whose citations do not resolve.

Mental model: A careful editor who removes any claim that cannot point to a source.

How To Start

  1. 1Use it to learn citation discipline before tackling multilingual generation.
  2. 2Implement the sentence-level citation filter exactly and inspect what gets deleted.
  3. 3Track coverage separately from support because strict filtering can make reports faithful but incomplete.

Watch out: It can produce very grounded reports, but broad topics can lose important facts if retrieval misses them or citation filtering deletes too much.

Build Recipe

  • Reformulate the report request into a concise retrieval query.
  • Use the RAGTIME API for first-stage recall, restricted to English for this reproduction.
  • Build a per-topic temporary passage index from retrieved documents.
  • Run both dense all-MiniLM retrieval and BM25 over the temporary index.
  • Fuse dense and BM25 rankings with reciprocal rank fusion and pass top passages to GPT-4o.
  • Require citations after every factual sentence and drop any sentence with unresolved citations.

Tools And Terms You Will See

RAGTIME APIBM25all-MiniLM-L6-v2RRFGPT-4oLlamaIndex-style citation mapping

Main Pitfalls

  • Strict postprocessing can delete useful but weakly cited content, hurting coverage.
  • Single-query retrieval is brittle for multifaceted topics.
  • Three no-output topics in the paper suggest citation filtering needs fallback handling.

Implementation Details That Matter

  • Separate recall and precision exactly as the paper does: remote API first, then local topic-specific dense/sparse reranking.
  • The local index is per topic, not a global corpus index, so you can implement it cheaply and inspect it for each request.
  • Citation filtering is deliberately harsh; implement a no-output fallback or at least log topics where every sentence is removed.
  • Use a sentence splitter that preserves bracket citations; stripping citations too early will destroy the document-id mapping.
  • This is English-only in the submitted run, so use it as a citation-grounding baseline before extending multilingual coverage.

Prompt / API Contracts

  • Reformulation prompt: return only a search query; do not include phrases like create a report, explain, or should include.
  • Generation prompt: answer using only provided sources; every factual statement must end with a bracket citation such as [2].
  • Generation prompt: keep the answer under the supplied character limit and include no uncited facts.
  • Postprocessor contract: remove uncited sentences, resolve citation numbers to source document ids, strip bracket markers, and store citation dictionaries.

Acceptance Checks

  • On a held-out topic, verify every retained sentence has at least one citation id that resolves to a retrieved document.
  • Track sentence deletion rate; if it is high, inspect retrieval or citation prompt failures before changing the generator.
  • Confirm character budget is checked after citation-marker removal and before result serialization.
  • Compare nugget coverage before and after strict sentence deletion to quantify the faithfulness-recall trade-off.

Implementation Skeleton

query = reformulate(request)
docs = ragtime_api.search(query, subset='eng')

  • The exact RAGTIME API response fields and any API-side ranking settings need to be mirrored or replaced explicitly.
  • The paper names LlamaIndex CitationQueryEngine behavior, but implementation details such as passage chunking and source-node metadata should be pinned in your reproduction.
  • The official paper reports three no-output topics; decide whether to reproduce that strictness or add a fallback as an experimental variant.

HLTCOE Rerank Fusion

Why this matters: Best leaderboard target for retrieval and long-report scoring, but harder to reproduce because the method is mostly documented through run descriptions and overview tables.

High difficultyHigh payoff1-2 weeks timebox

In Plain English

This is a high-scoring retrieval recipe. It combines several ranking systems, reranks their candidates, and fuses the rankings so documents that look good to multiple systems rise to the top.

Mental model: Several expert searchers each make a ranked list, then a judge combines their lists.

How To Start

  1. 1Reproduce the retrieval ranking before trying report generation.
  2. 2Keep PLAID-X, Qwen, and sparse-retrieval outputs as separate files so you can debug fusion.
  3. 3Treat this as an advanced target because some key details are only in run descriptions.

Watch out: It is probably powerful, but less transparent. Do not claim a faithful clone until model choices, fusion settings, and translation handling are pinned down.

Build Recipe

  • Assemble three first-stage or reranking signals: PLAID-X, Qwen-Embedding-8B, and multilingual LSR.
  • Use translations for reranking where available, but keep first-stage retrieval over original multilingual material when matching the run description.
  • Add pointwise or listwise rerankers such as jina-reranker-m0 or Qwen-based reranking.
  • Fuse rank lists with reciprocal rank fusion.
  • Feed the fused evidence set into a strong report generator, including GPT-5-family variants for the top long run.
  • Score retrieval and report generation separately so retrieval gains are not hidden by generation choices.

  • Start with the MLIR run before full report generation.

Implementation Details That Matter

  • Reproduce MLIR first because retrieval scores can be validated without the report generator confounding the result.
  • Keep each retrieval/rerank signal as a separate run file before fusion; this is the only way to debug whether RRF helps or just averages away a strong model.
  • Treat Searcher II, Qwen reranking, and jina-reranker-m0 as swappable layers with logged inputs and outputs.
  • When translations are used, log both original-language document ids and translated text ids so citation provenance remains on the original documents.
  • For the report-generation variant, freeze the fused retrieval set before changing generator prompts or model families.

Prompt / API Contracts

  • Reranker input contract: query or report request plus candidate document text; output a pointwise score or reordered list with stable document ids.
  • Fusion contract: accept independent ranked lists, not raw scores; use ranks so heterogeneous model scales do not require calibration.
  • Generator contract: consume the fused evidence set with original document ids preserved for citation mapping.

Acceptance Checks

  • Confirm you can reproduce a plausible MLIR ranking file with 1,000 documents per topic before any generation work.
  • Evaluate PLAID-X-only, Qwen-only, LSR-only, and fused variants to isolate the contribution of each signal.
  • Run an ablation with translations disabled during reranking to estimate how much of the gain depends on translation.
  • For long reports, score the same fused retrieval set with at least two generators to separate retrieval quality from generation quality.

Implementation Skeleton

rankings = [plaidx(query), qwen_embed(query), multilingual_lsr(query)]
reranked = [rerank_with_jina_or_qwen(r) for r in rankings]
fused = rrf(reranked)
report = generate_report(request, fused[:k])

Open Reproduction Unknowns

  • Searcher II is named in run descriptions but not fully specified in the available paper; pin the exact model and scoring prompt before claiming faithful reproduction.
  • Exact RRF constants, candidate depths, and per-language pooling settings are not all recoverable from the public run descriptions.
  • The generated-report prompting for the top hltime-gpt5.searcher run is less transparent than the retrieval recipe.

Primary reproduction target

HLTCOE Crucible Nugget-First Generation

Why this matters: Best target for studying why coverage improves: it makes predicted nugget quality the main planning artifact before generation.

High difficultyHigh payoff1-2 weeks timebox

In Plain English

This system plans the report around nuggets, which are small facts the final answer should cover. It predicts useful nuggets, finds supporting sentences for them, verifies citations, and assembles the report sentence by sentence.

Mental model: Write the outline as fact-sized cards, find evidence for each card, then turn the cards into a report.

How To Start

  1. 1Build a nugget lineage table for one topic: source document, nugget, supporting sentence, final sentence.
  2. 2Use the simpler Most Common nugget selector before attempting the SVC selector.
  3. 3Run support verification as an ablation so you can see what it helps and what it removes.

Watch out: The nugget selector is the heart of the system. If the chosen nuggets are weak, the final report cannot recover.

Build Recipe

  • Retrieve a broad document pool with BM25, PLAID-X, Qwen3, or LSR.
  • Summarize documents, then prompt an LLM to generate 1-6 nugget question-answer pairs per document.
  • Merge paraphrased nugget questions using embeddings plus LLM verification.
  • Filter non-answers and irrelevant nuggets; select the 10-20 most useful nuggets.
  • For each nugget, extract supporting sentences from source documents.
  • Generate the report from selected nuggets and citations, optionally verifying support with argue_eval.

  • The nugget selector is the system: weak nugget selection limits every downstream step.
  • Chunking for sentence extraction must avoid losing evidence across boundaries.

Implementation Details That Matter

  • The report is assembled sentence-by-sentence from selected nuggets, not written as one freeform answer from a large context window.
  • Preserve nugget provenance through all stages: source document, cluster id, selected canonical nugget, extracted sentence, confidence, and citation ids.
  • The SVC selector is a core component; if you cannot reproduce it, use Most Common as a transparent baseline and label the difference.
  • Citation verification is tightly coupled to the evaluation style, so include an ablation with verification disabled to understand the support/coverage trade-off.
  • The paper notes a DSPy misconception where some prompts ran without instructions; reproduce the intended field-level contract and document any divergence.

Prompt / API Contracts

  • Nugget ideation prompt: summarize each document and produce 1-6 question-answer nuggets that capture report-relevant facts.
  • SupportedAnswerExtractorRequest: given a document chunk, a nugget question, and candidate answers, extract a passage that substantiates an answer and rewrite it as a concise sentence.
  • SupportedAnswerabilityExtractorRequest: same extraction task but without an answer list; determine answerability directly from the chunk.
  • Verification prompt/API: remove citations where check_sentence_attested returns NO; optionally require check_nugget_matches for nugget coverage verification.
  • Report assembly: include at most one best sentence per selected nugget, remove low-confidence or duplicate sentences, then chop to length.

Acceptance Checks

  • For one topic, print a full nugget lineage table from source document through final sentence.
  • Run Most Common versus SVC selection on the same ideated nuggets and compare selected nugget overlap.
  • Measure sentence support before and after check_sentence_attested filtering.
  • Confirm the final report preserves the length budget after sentence-level chopping and metadata removal.

IDACCS Hybrid Extractive-LLM System

Why this matters: Best cost-controlled attribution target: it uses extraction as context compression, then lets an LLM refine or nuggetize the extract.

Medium difficultyMedium payoff4-6 days timebox

In Plain English

This system first makes an extractive summary, then lets an LLM polish or transform that extract. The extractive step compresses the source material and makes length control and attribution easier.

Mental model: Highlight the best source passages first, then ask a writer to turn the highlights into a report.

How To Start

  1. 1Reproduce retrieval, reranking, and occams extraction before adding GPT rewriting.
  2. 2Compare extract-only, nugget, and fluent-summary modes on the same evidence.
  3. 3Track output length because this method's advantage is length control.

Watch out: It is cost controlled and reproducible, but it may miss synthesis that requires combining facts across documents.

Build Recipe

  • Use PLAID-X to retrieve top documents per language from background plus problem statement.
  • Generate a better reranking query from title, background, and problem statement with GPT-4o.
  • Rerank 10-sentence chunks with mxbai-rerank-large-v1 and keep the top documents.
  • Create an occams extractive summary at roughly 2x target length or per-language budget.
  • Ask GPT-4.1 to produce nuggets, a fluent summary, or a direct extract from occams output.
  • Assign citations with the blame/miniblame attribution method.

Implementation Details That Matter

  • The extractive summary is a context-compression layer, not just a baseline; it is how the LLM sees salient evidence cheaply.
  • Keep the three GPT-4.1 modes separate: nugget formation, fluent summary composition, and extract-from-occams.
  • For multilingual long reports, maintain per-language extracts before synthesis so the 2,500-character per-language budget is enforceable.
  • The paper reports hybrid cost around one cent versus roughly fifty cents for an agentic system in related RAG submissions; track cost as a first-class metric.
  • The authors found occams default bigram behavior stronger than SPLADE-tokenized occams in their experiments; start with default occams before experimenting.

Prompt / API Contracts

  • GPT-4o rerank-query prompt: rewrite title, background, and problem statement into a focused query for reranking retrieved chunks.
  • GPT-4.1 nugget mode: form concise nuggets from the occams extract without exceeding the target length.
  • GPT-4.1 fluent mode: rewrite the extractive summary into a readable report while preserving cited facts.
  • GPT-4.1 extract mode: form an extract from the occams extract, favoring trivial attribution over abstraction.
  • Attribution contract: assign sentence-level citations after generation using blame/miniblame over the source document set.

Acceptance Checks

  • Verify chunk construction uses 10 sentences with 5-sentence overlap before reranking.
  • Compare GPT-4o and GPT-4.1 output lengths on the same occams extract to reproduce the undergeneration observation.
  • Score attribution separately from nugget coverage; the paper flags puzzling RAGTIME attribution behavior despite strong prior attribution performance.
  • Run a no-LLM extract-only variant to isolate how much GPT refinement helps or hurts coverage and support.

DUTH Lightweight MLIR Fusion

Why this matters: Best lightweight retrieval component target: useful if you want a reproducible MLIR baseline without heavy agent or LLM generation machinery.

Low difficultyMedium payoff2-3 days timebox

In Plain English

This is a compact retrieval baseline. It retrieves many candidate passages with BM25, reranks them with small cross-encoder models, then combines rankings.

Mental model: A lightweight search engine plus a small judge that reorders the first results.

How To Start

  1. 1Use it to smoke-test your indexing, run-file creation, and evaluation scripts.
  2. 2Keep BM25-only and each reranker output as separate baselines.
  3. 3Add fusion only after the individual rankings are working.

Watch out: It is helpful for learning and debugging retrieval, but it is not a full report-generation system and was not the top performer.

Build Recipe

  • Build a BM25 first-stage index and retrieve top 1,000 passages per topic.
  • Rerank candidates with compact cross-encoders such as MiniLM, ELECTRA, and TinyBERT.
  • Normalize scores where needed.
  • Fuse selected rank lists with linear fusion or reciprocal rank fusion.
  • Deduplicate and truncate to top 1,000 per topic in TREC run format.

  • Use this baseline to smoke-test evaluation scripts before spending GPU time on heavier rerankers.

LAS / Multiagent Research Workflows

Why this matters: Worth reproducing after the simpler systems: agentic workflows can improve coverage but are expensive, fragile, and harder to attribute.

High difficultyMedium payoff1-2 weeks timebox

In Plain English

This family uses multiple model roles, such as planner, researcher, writer, and reviewer. The agents call retrieval tools, pass evidence around, and revise the report.

Mental model: A small research team where one person plans, another gathers evidence, another writes, and another checks citations.

How To Start

  1. 1Build a single-agent baseline first, then add roles one at a time.
  2. 2Log every tool call and message so you can explain failures.
  3. 3Compare against GenAIus and WueRAG before paying the cost of multiagent runs.

Watch out: It can improve coverage, but it is expensive, variable, and harder to reproduce exactly.

Build Recipe

  • Start with a single agent using search as a tool, then add planner/researcher/writer roles.
  • Expose retrieval tools for PLAID-X, SPLADE/BM25, and dense retrieval.
  • Let a planner decompose the report request and assign research tasks.
  • Have a writer synthesize cited claims from collected evidence.
  • Add a reviewer or miniblame-style citation pass after writing.
  • Track cost, latency, output variance, and citation support separately from coverage.
